# AUTH.md

v1.0 uses a browser session without registration. The session is a signed token in an `HttpOnly` cookie set by the Backend. The Frontend never reads, stores or sends the token itself. Why: see [Tradeoffs](#tradeoffs).

## Modules

- `modules/users`: the `users` table and the CRUD of users. Fields: see [SCHEMAS.md](SCHEMAS.md#users-modulesusers).
- `modules/auth`: the session token, the authentication of a request and the owner check. No tables in v1.0. `auth` calls `users.services` to check that the user of a token exists: see [DESIGN.md](DESIGN.md#modules).
- `modules/main`: reads and sets the cookie, maps the result of `auth` to HTTP statuses: see [Access](#access).

## Session Flow

A user is needed only to create and manage listings. Search, Phone details and the "Deal" button work without a user, so a buyer never sees a form.

1. When the user opens any page, the Frontend calls `GET /api/users/me`. The browser sends the session cookie. On 200 the application header shows the loaded user: see [MY_LISTING.md](../features/MY_LISTING.md#edit-profile-flow).
2. On 401 there is no session. The My listings page shows a modal window for creating a user with the required fields. Fields: see [SCHEMAS.md](SCHEMAS.md#users-modulesusers).
3. The Frontend calls `POST /api/users`. The Backend creates the user, sets the session cookie and returns the user.
4. Every later request carries the session cookie. A request with an invalid session returns 401 and the Backend removes the cookie, so the Frontend shows the modal window from step 2.

The Frontend sends every API request with `credentials: "include"`. There is no session data in `localStorage` or in other browser storage.

## User ID

- In PostgreSQL the user ID is stored in the `id` field of the `users` table (primary key).
- The `id` is generated by PostgreSQL on insert: column default `gen_random_uuid()` (UUID v4). The Backend and the Frontend do not generate it, and the client cannot choose its own `id`.
- The user ID is not a credential. `GET /api/users/me` returns it.

## Session Token

- The token is `<user_id>.<signature>`: the HMAC-SHA256 signature of the user ID with `SESSION_SECRET`, base64url. Python standard library `hmac`, the signature is compared in constant time.
- The token has no expiration in v1.0.
- `modules/auth` issues and verifies the token. The secret is passed by `modules/main`: `modules/auth` has no settings of its own. Variables: see [DESIGN.md](DESIGN.md#configuration).
- A changed `SESSION_SECRET` invalidates all sessions.

## Cookie

| Attribute | Value |
| --- | --- |
| Name | `session` |
| `HttpOnly` | yes: JavaScript cannot read the cookie |
| `Secure` | `COOKIE_SECURE`, `true` by default, `false` only for local HTTP development |
| `SameSite` | `Lax` |
| `Path` | `/api` |
| `Max-Age` | 400 days, the browser maximum |

- `modules/main` sets the cookie again on every response of a request with a valid session. The session ends only after 400 days without a visit.
- CORS allows credentials for the origins from `CORS_ORIGINS` only. `*` is not allowed.

## Access

- Access levels: `Public`, `User`, `Owner`. The level of every endpoint: see [API.md](API.md).
- `User` and `Owner` endpoints require a valid session. `modules/auth` verifies the signature and checks that the user exists. The result is the current user.
- `Owner` endpoints: the current user must be the owner of the resource in the path. A user reads, updates and deletes only own resources. Ids are compared as UUIDs.
- The checks are FastAPI dependencies in `modules/main`: see [modules/main/CLAUDE.md](../../backend/modules/main/CLAUDE.md#code).
- Statuses: missing cookie, invalid signature or unknown user 401 (the cookie is removed), malformed or unknown resource id 404, the current user is not the owner 403.
- Public endpoints never return the user ID of a listing owner. The contact of a listing owner is returned by `GET /api/phones/{id}/contact` by the listing ID.

## Tradeoffs

### No registration in v1.0

v1.0 has no registration and no login, as required by [TASK.md](../../TASK.md#out-of-scope-for-v10). The PoC is used to collect feedback, so a user only needs to try the product once or twice.

### Signed token in an HttpOnly cookie

- Chosen: a signed token without a table. JavaScript has no access to the token, so an XSS cannot copy the session. The user ID is not a credential and can be returned to the Frontend.
- Rejected: the user ID in `localStorage` with the `X-User-Id` header (the previous version). Any script on the page can read it, and the user ID works as a bearer token.
- Rejected: the user ID in the cookie. The user ID stays a credential and cannot be returned to the Frontend.
- Rejected for v1.0: a `sessions` table with a random token. It adds logout and revocation of one session, both are out of scope for v1.0.
- CSRF: `SameSite=Lax` blocks the cookie on cross-site `POST`, `PUT`, `PATCH` and `DELETE`. JSON requests need a CORS preflight, and CORS allows only `CORS_ORIGINS`.

### Limitations

- A session is tied to one browser. Cleared cookies or another device create a new user. The previous listings stay with the old user and are not accessible.
- There is no logout and no expiration of the token. A session cannot be revoked alone, only all sessions together by a new `SESSION_SECRET`.
