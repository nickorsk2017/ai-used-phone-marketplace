# Second-Hand Mobile E-market

Author: Nikolai Stepanov, [LinkedIn](https://www.linkedin.com/in/nickot)

A web app for selling second-hand mobile phones in the US market. A buyer finds a phone with one prompt instead of pages of filters, for example `Samsung with a good camera and a long battery life, like new, under $400`. A seller creates a listing, and the model description is generated by AI.

Version v1.0 is a PoC to validate the idea and collect user feedback. Product requirements: [TASK.md](TASK.md). Architecture: [BRIEF.md](BRIEF.md).

> **PoC, not a commercial product.** v1.0 is built only to validate the business idea, as required by [TASK.md](TASK.md#business-requirements). Simplifications such as the browser session without registration are intentional and follow the [v1.0 scope](TASK.md#out-of-scope-for-v10): see [What is real and what is stubbed](BRIEF.md#what-is-real-and-what-is-stubbed). The path to production: [TODO.md](docs/TODO.md).

## Problem

Buyers of a phone spend hours on store websites and marketplaces: they set filters, open dozens of product pages and compare specifications, prices and reviews. The decision can take days. The app replaces pages of filters with one prompt: the buyer describes the phone in own words and gets matching listings in minutes. Full description of the problem, the business requirements and the v1.0 scope: [TASK.md](TASK.md).

## Documentation as the source of truth

Documentation is the basis of development: the system is designed first, the code is written after that. The approach is used for code quality, not for the test task: the agent generates code from a reviewed design, the Validator checks the code against it, and every decision has one source of truth.

1. Every product decision, module, data model and API contract is described in `docs/` before implementation.
2. The Claude agent generates code from the documentation and follows the rules in [CLAUDE.md](CLAUDE.md) and in the `CLAUDE.md` of each subsystem.
3. Each fact is described in one document only. Other documents link to it.
4. A change in behavior starts with a change in the documentation. Code follows the documentation.
5. If the documentation and the code disagree, the agent does not resolve the conflict silently. It lists the discrepancies for the Engineer to fix.

## Getting started

Requirements: Docker with Docker Compose, an OpenAI API key. PostgreSQL with pgvector runs in a container.

```bash
cp backend/.env.example backend/.env
cp frontend/.env.example frontend/.env
make up
```

The first two commands create the environment files. Fill in `POSTGRES_PASSWORD`, `SESSION_SECRET` and `OPENAI_API_KEY` in `backend/.env`. `make up` builds the images, starts PostgreSQL, applies the Alembic migrations and starts the `frontend` (http://localhost:3000) and `backend` (http://localhost:8000) services. `make down` stops them. Details: [INFRA.md](docs/INFRA.md#docker-compose).

## Deployment

Deployment goes through GitHub pull requests: `dev` is the development branch, `production` is the deployed version. A pull request from `dev` into `production` releases a new version. Details: [INFRA.md](docs/INFRA.md#build-and-deployment).
