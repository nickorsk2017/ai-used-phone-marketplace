# Second-Hand Mobile E-market

Author: Nikolai Stepanov, [LinkedIn](https://www.linkedin.com/in/nickot)

A web app for selling second-hand mobile phones in the US market. A buyer finds a phone with one prompt instead of pages of filters, for example `Samsung with a good camera and a long battery life, like new, under $400`. A seller creates a listing, and the model description is generated by AI.

Version v1.0 is a PoC to validate the idea and collect user feedback. Product requirements: [TASK.md](docs/TASK.md). Architecture: [DESIGN.md](docs/DESIGN.md).

## Problem

Buyers of a phone spend hours on store websites and marketplaces: they set filters, open dozens of product pages and compare specifications, prices and reviews. The decision can take days. The app replaces pages of filters with one prompt: the buyer describes the phone in own words and gets matching listings in minutes. Full description of the problem, the business requirements and the v1.0 scope: [TASK.md](docs/TASK.md).

## Known limitations

- Model codes from the LLM can be wrong for rare models, and one model can have several codes: see [RAG.md](docs/ai/RAG.md#model-code-limitations).
- A session is tied to one browser, there is no logout: see [AUTH.md](docs/backend/AUTH.md#limitations).
- After a listing is updated or deleted, the Phone details page shows the previous version for up to 60 seconds: see [PHONE_DETAILS.md](docs/features/PHONE_DETAILS.md#time-based-revalidation-only).

Each document has a Tradeoffs section with the rationale and the limitations of its decisions.

## Documentation as the source of truth

The project is designed in the documentation first. Code is generated after that, and the documentation is the main reference for the Claude agent.

1. Every product decision, module, data model and API contract is described in `docs/` before implementation.
2. The Claude agent generates code from the documentation and follows the rules in [CLAUDE.md](CLAUDE.md) and in the `CLAUDE.md` of each subsystem.
3. Each fact is described in one document only. Other documents link to it.
4. A change in behavior starts with a change in the documentation. Code follows the documentation.
5. If the documentation and the code disagree, the agent does not resolve the conflict silently. It lists the discrepancies for the Engineer to fix.

## Getting started

Requirements: Docker with Docker Compose, a Supabase project with the pgvector extension, an OpenAI API key.

```bash
cp .env.example .env
docker compose up --build
make migrate
```

The first command creates the environment file. Fill in the Supabase connection and the OpenAI API key in `.env`. The second command builds and starts the `caddy`, `frontend` and `backend` services. The third command applies the Alembic migrations of all Backend modules to Supabase.

## Deployment

```bash
make deploy
make logs
```

`make deploy` pulls the latest images from GHCR on the VPS and restarts the services. `make logs` shows the service logs. The images are built by GitHub Actions on push to the main branch. Details: [INFRA.md](docs/INFRA.md#build-and-deployment).
