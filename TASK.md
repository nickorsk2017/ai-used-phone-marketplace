# Second-Hand Mobile E-market

Author: Nikolai Stepanov

## Product

A web app for selling second-hand mobile phones.

Market: the United States only. The product is not designed for the global market in v1.0. Prices are in USD, phone models and model codes are the US versions.

## Problem

Buyers can spend hours researching smartphones across different websites.
They compare specifications, prices and reviews before making a decision.
The whole process can take days or weeks.

Typical scenario of a user who has not yet chosen a model:

1. Visits store websites and marketplaces.
2. Sets filters by price, brand, storage and other specifications.
3. Browses dozens of models and opens product pages.
4. Compares specifications, prices, user reviews and expert reviews.
5. Returns to several options, compares them again and makes a decision.

## Business Problem

For a marketplace of used phones the long search is a loss of revenue:

- Lost buyers. A buyer who cannot find a suitable phone in a few minutes leaves for a competitor or postpones the purchase. The marketplace pays for the traffic and loses the sale.
- Lost sellers. Fewer buyers mean fewer deals, and sellers move to platforms with more demand.
- No differentiation. Marketplaces of used phones offer the same filters and the same catalog. The search experience is one of the few areas where a marketplace can stand out.

Hypothesis of v1.0: search by one prompt shortens the time from the first visit to the Deal click and increases the share of visits that end with a Deal click. The PoC validates the hypothesis on the first users: see the online metrics in [TODO.md](docs/TODO.md#production-baseline).

## Solution

An AI service that lets the user find the right phone with a prompt in minutes instead of pages of filters.

## Where AI fits and where it does not

AI is used where the input is free text:

- Understanding the buyer's prompt: needs, preferences and constraints written in natural language.
- Generating the model description and the model data from the model name.
- Ranking listings by relevance to the request.
- Catching fraud and prompt injection that regex does not catch.

AI is not used where the result must be exact:

- Price and condition are exact filters. The LLM only extracts them from the prompt, the filtering is done by SQL.
- Creating, updating and deleting listings and access checks are deterministic code.
- The WhatsApp number is not processed by the LLM.

AI risks:

- Phone specifications (camera, battery, display) and model codes are returned by the LLM and can be wrong, especially for rare models: see [RAG.md](docs/ai/RAG.md#model-code-limitations). For this reason, the seller reviews the generated data before the listing is published and can edit the description and the specifications. The model code is not shown to the seller in v1.0: see [MY_LISTING.md](docs/features/MY_LISTING.md#description-response).
- The LLM can misread the prompt, for example miss the price or the condition.

## Business requirements

1. MVP prototype (v1.0) to validate the idea (PoC), show it to users and collect feedback.
2. No architecture for millions of requests is needed, but it is built with quality for further use.
3. Antifraud filter. Creating listings that contain credit card numbers, websites or phone numbers is prohibited (except the WhatsApp number stored in the account, which is shown separately from the listing text).
4. Three main pages:
   - **My listings.** The user's list of listings, including a modal window for creating a new listing. The window contains a model description that can be generated by AI. A comment about the phone condition is free text (new, with scratches). The user selects a fixed phone condition value (like new, average condition, for repair) from a list. The user enters the price in USD.
   - **Search.** A single prompt field and a list of phones matching the query. There are no separate filter controls. Condition and price are taken from the prompt, for example "like new under 300 dollars". Rules: see [SEARCH_PAGE.md](docs/features/SEARCH_PAGE.md#condition-and-price).
   - **Phone details.** Model description, price, the user's note about the phone condition and a "Deal" button. The button opens a modal window with the WhatsApp number and a "Copy WhatsApp number" button. WhatsApp integration is not needed for v1.0, the user pastes the number manually. This page must have SEO.
5. Phone parameters used by the search: OS (iOS / Android), model, camera, battery, display. Listing fields used by the search: condition and price (USD), taken from the prompt. Other parameters are not considered in this version. Search by other parameters is possible through the model description.

## Out of scope for v1.0

- Complex authorization and registration logic. Only a browser session is used. Short feedback is collected separately through communication channels. Forcing registration loses leads.
- Complex search logic. A single prompt is enough.
- Complex cases. The goal is a PoC (Proof of Concept), not 1000 scenarios.
- Complex design, images, logos, animation, special effects. Focus on UI usability and a good first impression. A lightweight interface. Ready-made UI components are preferred over custom libraries at this stage.
